# M0 게임 루프 상세 스펙

- 작성: 2026-07-26
- 상태: **M0 기능·명령 멱등성·production protocol 인수 완료** (외부 provider 계정 authorization/callback만 owner 수동 확인)
- 상위 계획: [`development-plan.md` §2, §4.2, §12](./development-plan.md)

## 1. 목표와 범위

M0의 구현 목표는 **서버 소유 게임일 전진을 수동 스텝과 배속·일시정지 양쪽에서 같은 일일
파이프라인으로 실행**하는 것이다. 이번 범위는 기능과 무결성까지이며 시각적 스타일링은 포함하지 않는다.

이미 구현된 인증, 캐릭터 생성, MySQL 세이브, SSE, 클라이언트 기반 레이어 위에 다음을 더한다.

- 수동 1일·1주·1개월 진행을 하루씩 순서대로 커밋
- x1·x2·x4·x8 서버 배속과 일시정지
- 매 게임일 커밋 뒤 사용자별 SSE 틱 전송
- 캐릭터 생성 전 전진 차단
- 계정당 세이브 하나와 세이브별 전진 직렬화

M0 시점의 시장 조회·평가·정산·이벤트 단계는 빈 훅으로 시작했다. M1~M5 구현은 이 일일 파이프라인 안에
순서대로 추가됐고, 현재 production도 같은 하루 단위 commit 경계를 사용한다.

M0에는 랭킹이 없으므로 기존 전체 필드 편집은 개발용 비랭크 시작으로 둔다. 프리셋 선택이 기본 흐름이며,
포인트 예산 검증과 랭크·샌드박스 모드 분리는 M5에서 서버 계약과 함께 도입한다.

## 2. 수동 진행 계약

- `POST /api/advance`는 canonical UUID `commandId`, 최초
  `expectedRunRevision · expectedStateRevision · expectedGameDay`, `days`를 받는다. `days` 범위는
  `1..=30`이고 M0 UI는 1·7·30만 보낸다.
- 서버는 요청을 하루 단위로 반복하고 매일 DB 커밋 후 SSE `tick`을 보낸다.
- HTTP 응답은 `advance { commandId, requestedDays, initialCursor, committedCursor, replayed }`와 반복이
  끝난 최신 스냅샷을 함께 가진다.
- 수동 진행 요청은 실행 중인 배속을 먼저 정지한다.
- 같은 세이브의 수동·자동 진행과 캐릭터 재생성은 하나의 전진 잠금으로 직렬화한다.
- 캐릭터가 없는 세이브는 `409 Conflict`로 거부한다.
- 계정당 세이브 유니크 제약을 추가하기 전에 과거 생성 경쟁으로 생긴 중복을 정리한다. 이전 저장소가
  항상 가장 낮은 세이브 ID만 사용했으므로 그 행을 보존하고, 이후 한 번도 도달할 수 없었던 높은 ID
  행은 자식 캐릭터와 함께 제거한다.

응답 유실과 중간 실패에도 날짜를 중복 진행하지 않도록 명령 기록을 세 층으로 둔다.

- `command_identity`는 세이브 안에서 UUID를 전역으로 선점하고 명령 종류, canonical payload SHA-256,
  최초 커서를 append-only로 보존한다. 같은 UUID의 다른 종류나 payload는 항상 충돌이다.
- `advance_command_step`은 `(commandId, stepNo)`별 전후 커서를 해당 날짜 변경과 같은 트랜잭션에
  append-only로 기록한다.
- `command_receipt`는 요청한 모든 날짜가 끝난 마지막 step과 같은 트랜잭션에서만 완성 결과를 기록한다.

1일 뒤 3일 명령이 실패하면 재시도는 저장된 step 다음 날부터 남은 2일만 실행한다. 완료 응답을 잃은 뒤
같은 요청을 다시 보내면 receipt와 현재 스냅샷을 반환하고 날짜나 SSE를 다시 만들지 않는다. 다른 명령이
미완료 명령 사이에 커서를 바꿨다면 자동으로 건너뛰지 않고 `busy`로 거절한다. DB commit과 SSE 전송 사이
프로세스가 종료되면 재연결의 최신 스냅샷으로 수렴하며, 이미 commit된 tick의 네트워크 재전송 보장은
후속 outbox 범위다.

### 2.1 캐릭터 시작 명령

`POST /api/characters`도 `commandId`, 현재 스냅샷의 세 expected cursor, `character` draft를 받는다.
성공 응답은 `start { commandId, committedCursor, replayed }`와 최신 스냅샷이다. 세이브 잠금 아래 identity와
receipt를 먼저 검사하고, 새 명령이면 활성 시장·policy assignment를 다시 확인한 뒤 이전 런 종료, 새 런,
기본 계좌와 opening 원장, 캐릭터, receipt를 한 트랜잭션에 커밋한다. 응답 유실 뒤 같은 요청을 재생해도
run revision은 한 번만 증가한다.

서버는 필드가 없는 구형 요청에 UUID를 대신 만들지 않는다. 그런 요청은 mutation 전에 `invalidCommand`로
거절해 클라이언트 새로고침을 유도한다. 클라이언트는 네트워크 오류나 5xx처럼 성공 여부를 모르는 동안
원 command ID·cursor·payload를 보존하고, 성공 또는 확정적인 도메인 거절을 받은 뒤에만 버린다. 그 사이
SSE가 앞선 스냅샷을 보내도 재시도 body를 새 커서로 바꾸지 않는다.

## 3. 배속·일시정지 계약

클라이언트는 `POST /api/clock`으로 원하는 상태를 보낸다.

```json
{ "speed": 4 }
```

`speed`는 `1 | 2 | 4 | 8 | null`이다. 숫자는 시작 또는 속도 변경, `null`은 일시정지다.
응답은 명령이 반영된 `GameSnapshot`이고, 스냅샷의 `autoSpeed`도 같은 값이다.

| 속도 | 게임 1일 사이 최소 간격 | 이론상 최대 처리량 |
|------|------------------------|--------------------|
| x1 | 500ms | 2일/초 |
| x2 | 250ms | 4일/초 |
| x4 | 125ms | 8일/초 |
| x8 | 62ms | 약 16일/초 |

- 첫 자동 스텝은 선택한 간격이 지난 뒤 실행한다.
- 다음 타이머는 이전 하루의 커밋과 푸시가 끝난 뒤에만 예약한다. 지연된 틱을 몰아서 실행하지 않고
  요청도 겹치지 않으므로 실제 속도는 표의 상한보다 느릴 수 있다.
- 서버는 세이브당 자동 실행기 하나만 둔다. 같은 요청은 유지하고 다른 속도는 기존 타이머를 교체한다.
- 자동 실행 상태는 런타임 제어 상태이며 DB에 저장하지 않는다. 서버 재시작 뒤에는 정지 상태다.
- 캐릭터 생성 또는 새 캐릭터로 재시작하면 자동 실행을 정지한다.

## 4. 온라인 생명주기

M0 자동 진행은 **현재 브라우저 세션이 연결된 동안만** 돈다.

- 자동 실행 시작에는 해당 사용자의 활성 SSE 연결이 하나 이상 필요하다. 없으면 `409 Conflict`다.
- 사용자의 마지막 SSE 연결이 닫히면 서버가 자동 실행을 정지한다.
- 여러 탭이 연결돼 있으면 마지막 탭이 닫힐 때까지 연결 상태로 본다.
- 클라이언트는 탭이 숨겨지면 SSE를 닫고, 다시 보이면 연결한다. 따라서 숨긴 동안에도 기본적으로 정지한다.
- 네트워크 단절도 연결 종료이므로 자동 실행을 정지한다. 재연결 뒤 사용자가 다시 속도를 선택한다.

오프라인 자동 진행 토글과 최대 90일 따라잡기는 M5 범위다. 이 기능은 DB에 명시적으로 동의 상태와
마지막 처리 시점을 저장하는 별도 배치로 구현하며 M0 온라인 실행기를 연장해 흉내 내지 않는다.

## 5. 스냅샷과 클라이언트

`GameSnapshot`은 기존 필드에 다음 두 값을 추가한다.

- `runRevision: number` — 캐릭터를 새로 만들 때마다 증가하는 세이브 실행 세대. DB에 저장한다.
- `autoSpeed: 1 | 2 | 4 | 8 | null` — 현재 런타임 배속. DB에 저장하지 않는다.

- 대시보드는 x1·x2·x4·x8와 일시정지 컨트롤을 제공한다.
- 자동 실행 중에는 수동 스텝 버튼을 비활성화한다.
- 속도 명령 처리 중에는 중복 명령을 막고, 실패하면 정지 상태를 다시 조회한 스냅샷에 맡긴다.
- 연결 중인 클라이언트는 같은 게임일의 배속 변경을 순서가 보장된 SSE에서 적용한다. 배속 HTTP 응답은
  성공 여부 확인에 쓰며, 늦은 응답이 더 최신 일시정지를 덮지 않게 한다.
- 수동 진행 HTTP 응답은 현재 스냅샷보다 실행 세대나 게임일이 실제로 앞설 때만 보완 적용한다. 같은
  게임일까지 이미 SSE로 받은 경우에는 그 뒤에 도착한 배속 상태를 보존한다.
- HTTP 응답과 SSE가 엇갈리면 실행 세대가 작은 스냅샷을 버리고, 실행 세대가 같을 때는 `gameDay`가
  현재보다 작은 스냅샷을 버린다. 세대가 크면 새 캐릭터의 0일차를 정상 적용한다.
- 캐릭터 생성 응답도 같은 스냅샷 적용 관문을 거쳐, 다른 탭에서 더 나중에 시작한 실행 세대를 되돌리지
  않는다.
- 캐릭터가 없는 첫 스냅샷은 `/new`로 이동시킨다. 스냅샷 미수신 상태와 캐릭터 없음은 구분한다.
- 의도적으로 SSE를 닫은 탭 숨김은 연결 장애 토스트를 띄우지 않는다.

## 6. 완료 조건

1. 로그인한 신규 계정이 프리셋을 골라 캐릭터를 만든다.
2. 1일·1주·1개월 진행에서 게임일이 각각 하루씩 커밋되고 틱도 같은 순서로 도착한다. 중간 실패와 최종
   응답 유실 재시도에서도 이미 끝난 step은 다시 실행되지 않는다.
3. x1·x2·x4·x8 선택 후 게임일이 연속 증가하고 속도 변경이 중복 실행기를 만들지 않는다.
4. 일시정지, 탭 숨김, 마지막 SSE 연결 종료, 캐릭터 재생성에서 추가 진행이 멈춘다.
5. 캐릭터 없는 세이브, 지원하지 않는 속도, 30일을 넘는 수동 요청을 서버가 거부한다.
6. 클라이언트 타입 검사·단위 테스트·프로덕션 빌드와 서버 테스트·clippy·fmt가 통과한다.

### 6.1 최종 인수 (2026-07-30)

- M1~M5의 실제 production 장기 검증이 M0 `command_identity → advance_command_step → command_receipt`
  재개 계약을 그대로 사용했다. ranked preset의 마지막 30일 처리 중 day 10,949에서 정산 오류가 발생했을
  때 앞선 29개 하루 commit이 보존됐고, 같은 command ID와 최초 cursor로 재시도해 day 10,950 receipt와
  finalization 한 건으로 수렴했다. 새 command와 과거 cursor는 `409 busy`로 거절됐다.
- production `/api/auth/providers`는 DataGSM·Google 두 provider만 반환하고 canonical client `/login`도 두
  버튼을 표시한다. 두 start endpoint는 transaction cookie를 만들고 각 provider authorization endpoint로
  `303`을 반환했다. 실제 외부 계정의 authorization/callback은 계정 접근 승인이 필요한 owner 수동 smoke이며,
  서버 기능 또는 M0 완료의 미구현 항목으로 세지 않는다.
- 전체 server `cargo clippy --all-targets -- -D warnings`와 `cargo fmt --check`, client typecheck·lint·build는
  최종 M5 인수에서 다시 통과했다. M0의 기능·무결성 목표는 완료다.

## 7. 후속 작업

- M1 시장 생성·조회·포지션 평가, M2 정산 큐, M5 오프라인 진행과 ranked/sandbox 정책은 모두 완료됐다.
- SSE는 재연결 때 최신 authoritative snapshot으로 수렴한다. 과거 tick 자체의 `Last-Event-ID` outbox 재생은
  현재 snapshot protocol의 정확성에 필요하지 않은 post-M5 확장 범위이며 M0~M5 미완료로 세지 않는다.
