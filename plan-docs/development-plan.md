# LifeLedger 개발 계획

> 모의 자산 관리 인생 시뮬레이션 웹게임. 실제 금융 제도와 시장 통계를 기반으로 돌지만
> 플레이어의 자산만 가상이다. 비상업적 개인 프로젝트.

- 최초 작성: 2026-07-25
- 최근 갱신: 2026-07-29
- 상태: M4-E2b·E2c와 법인 기능 화면 로컬 구현 완료, production migration 49·50 인수 대기, 시각 스타일링 보류

---

## 1. 제품 개요

플레이어는 **캐릭터를 생성해 시작 조건을 직접 정하고**(나이·성별·출신·시작 자금·부채 등, §3),
그 조건에서 증권·연금·부동산·현물·예금 등에 자산을 배분하며 불려 나간다.
그 위에 취업·법인 설립·개인파산 같은 생애 이벤트와, 그 이벤트를 가능하게 하는 개인 스펙
(학력·자격증·연수·경력·프로젝트)이 얹힌다. 인생게임이지만 무게중심은 **자산 관리**에 있다.

### 핵심 재미

1. **실제 제도를 이용한 최적화** — ISA·연금저축·IRP의 한도와 세제 혜택을 조합해 세후 수익을 끌어올리는 재미
2. **시장 사이클 경험** — 금리 인상기·침체·회복이 자산군별로 다르게 작용하는 것을 체감
3. **인적 자본과 금융 자본의 상호작용** — 스펙에 투자해 소득을 올리는 것과 금융에 투자하는 것 사이의 배분
4. **다른 출발선 다시 살기** — 19세 고졸 무자본과 38세 부채 보유자의 최적해는 완전히 다르다. 리플레이의 동력

### 비범위 (이 프로젝트가 하지 않는 것)

- 실제 금전 거래, 실제 주문 체결, 실제 계좌 연동
- 투자 조언 · 수익률 예측 제공
- 특정 금융회사 상품의 광고 또는 비교 추천

## 2. 확정된 핵심 설계 결정

| 항목 | 결정 | 근거 |
|------|------|------|
| 시간 모델 | **플레이어 제어** — 수동 스텝 + 배속 실행 + 일시정지 | 재무 의사결정에는 생각할 시간이 필요하다. 벽시계에 끌려가면 답답하고, 자리를 비운 사이 손실이 나면 억울함 |
| 클록 | **플레이어별 게임일 커서** (전진만, 되감기 없음) | 각 세이브가 자기 게임일을 가진다 |
| 시장 시계열 | **시드 기반 결정론적 시계열. 전원 게임일 0에서 출발** | 모든 플레이어가 같은 시장을 같은 순서로 겪는다 → 랭킹이 동일 조건 비교가 됨 (§2 아래) |
| 진행 단위 | 수동 = 1일 / 1주 / 1개월 스텝, 자동 = 게임 1일당 실제 0.5s ~ 0.05s (x1~x8) | 서버가 스텝을 실행하고 클라이언트는 요청만 한다 |
| 오프라인 진행 | 기본 정지. "자동 진행" 토글 시 상한(예: 게임 90일)까지 서버가 이어 진행 | 방치형을 원하는 사람만 켠다 |
| 시뮬레이션 해상도 | **게임 1일 봉** (장중 틱 없음) | 자산 배분 게임에 초 단위 호가는 불필요. 부하·복잡도 절감 |
| 시작 조건 | **프리셋 + 포인트 예산 내 커스텀** (§3) | 자유 입력만 두면 밸런스가 붕괴. 랭크/샌드박스 모드 분리 |
| 실제 수치 | **3자 혼합** — 과거 시계열로 모델 캘리브레이션 + 외부 API로 현재값 앵커링 + 제도·상품 스펙은 실제 규정대로 | 재현성·법적 안전성·현실감을 동시에 확보 |
| 저장·계정 | **서버 계정 + MySQL** | 서버가 세이브와 정산의 권위. 랭킹·치팅 방지·기기 간 이어하기. DB 선택 근거는 §4.3 |
| 시뮬레이션 권위 | **서버 단독** | 클라이언트는 표현만. 금액 계산을 클라이언트에 두면 조작 가능 |

### 시간을 플레이어에게 준 결과

플레이어별 클록으로 바꾸면서 **모두가 게임일 0에서 같은 시장 시계열을 출발**하게 됐다.
공유 벽시계였다면 있었을 "늦게 시작하면 세계 중간에 합류한다"는 불공정이 아예 사라진다.
남는 불공정은 **시작 조건 커스텀**뿐이고, 이건 **프리셋별 리그 분리**로 처리한다
(난이도 계수를 곱해 한 표에 섞는 방식보다 단순하고 납득 가능하다).
포인트 예산으로 커스텀한 캐릭터는 예산이 같은 리그에, 샌드박스는 랭킹에서 제외.

랭킹 지표는 **고정 목표 시점(예: 게임 30년) 도달 시의 세후 순자산**을 쓴다. 경과 연수가 서로 달라도
비교할 수 있어야 했던 CAGR 정규화가 이제 필요 없다.

**대신 새로 생기는 문제: 메타 지식.** 시계열이 결정론적이고 모두 같은 시드를 쓰면
"게임 4년차에 폭락이 온다"가 공유되는 순간 최적해가 고정된다. 두 갈래로 처리한다.

- **랭크 모드** — 시즌 공통 시드. 시즌이 끝나면 시드를 교체해 공략을 무효화한다 (§11 시즌제와 연결)
- **자유 모드** — 캐릭터별 개인 시드. 파라미터는 같아 난이도는 통계적으로 동일하되 전개는 매번 다름

## 3. 캐릭터 생성 (시작 설정)

시작 조건은 이 게임의 리플레이 축이다. **자금 1,000만원은 기본 프리셋의 값일 뿐 고정값이 아니다.**

### 3.1 시작 파라미터

| 파라미터 | 범위 | 게임 내 영향 |
|----------|------|--------------|
| 나이 | 19 ~ 50 | 남은 경제활동 기간, 청년 대상 정책상품 자격, 연금 수령 개시까지의 기간, 채용 공고 연령 밴드 |
| 성별 | 남 / 여 / 기타 | **제도적으로 실재하는 차이에만 연결** (§3.4) |
| 병역 상태 | 미필 / 복무중 / 필 / 면제 / 특례복무 | 채용 공고 자격 제약, 경력 공백, 복무 기간 소득·자산 제약 (§8.1) |
| 출신 지역 | 수도권 / 광역시 / 중소도시 / 군 | 부동산 가격대, 공고 풀(사랑방 유효성), 생활비 수준 |
| 가정 배경 | 지원형 / 독립형 / 부양형 | 부모 지원금 수령, 부양비 고정 지출, 상속 이벤트 확률 |
| 학력 | 고졸 ~ 박사 | 초기 스펙, 학자금 부채와 연동, 초임 밴드 |
| 경력 | 0 ~ n년 | 시작 연봉 밴드, 경력직 공고 접근 |
| 보유 자격증 | 0 ~ n | 초기 스펙 |
| 시작 자금 | 0 ~ 예산 상한 | 현금·예금 배분 상태로 지급 |
| 시작 부채 | 학자금 / 신용 / 전세대출 | 원리금 상환 스케줄, 신용점수 초기값, DSR 여력 |
| 건강 | 상 / 중 / 하 | 의료비 이벤트 확률, 보험료율 |
| 부양가족 | 0 ~ n | 고정 지출 증가, 소득공제 증가 |

### 3.2 밸런스 — 포인트 예산

자유 입력만 허용하면 "시작 자금 100억 / 부채 0 / 19세"가 유일해라서 게임이 성립하지 않는다. 두 모드로 나눈다.

- **랭크 모드** — 프리셋을 고르거나, 포인트 예산 안에서 트레이드오프로 배분한다.
  자금을 올리면 나이·부채·건강·부양가족에서 대가를 치른다. 예산이 같은 캐릭터끼리 같은 리그
- **샌드박스 모드** — 모든 값 자유 입력. 랭킹 제외. 제도 실험용

M0에는 랭킹이 없으므로 현재 캐릭터 편집 폼은 **개발용 비랭크 시작**으로 취급한다. 프리셋 선택 흐름을
완료 기준으로 삼되, M5에서 포인트 예산을 도입할 때 랭크 모드와 샌드박스 모드를 서버 계약부터 분리한다.

### 3.3 프리셋 (초기 제공안)

| 프리셋 | 나이 | 학력 | 시작 자금 | 부채 | 배경 | 성격 |
|--------|:---:|------|-----------|------|------|------|
| 사회초년생 | 25 | 학사 | 1,000만 | 학자금 2,000만 | 독립형 | 기본값. 균형 |
| 이른 출발 | 19 | 고졸 | 200만 | 없음 | 부양형 | 시간은 많고 자본은 없음 |
| 늦은 출발 | 38 | 학사 | 5,000만 | 신용 3,000만 | 독립형 | 자본은 있고 시간이 짧음 |
| 지원 받는 출발 | 25 | 석사 | 3억 | 없음 | 지원형 | 쉬운 난이도. 세제 한도 최적화가 주 과제 |
| 재기 | 45 | 고졸 | 0 | 회생 이력 | 독립형 | 신용 제약 하에서의 복구 플레이 |

수치는 플레이테스트로 조정한다. 프리셋도 콘텐츠 데이터로 관리해 코드 수정 없이 추가한다.

### 3.4 성별 처리 원칙

성별은 **제도적으로 실재하는 차이에만** 연결한다.

- 병역 대상 판정 (§8.1) → 복무 기간이 경력 공백·자산 공백으로 반영
- 출산·육아 관련 제도 (육아휴직 급여, 관련 공제)
- 성별에 따라 산정되는 보험료율

반대로 **채용 확률·연봉에 성별 계수를 직접 넣지 않는다.** 현실의 격차를 재현한다는 명목으로
차별을 게임 규칙으로 고정하는 것은 이 프로젝트가 할 일이 아니다. 격차를 다루더라도
제도(경력 단절, 휴직)를 통해 간접적으로 드러나게 한다.

### 3.5 정합성 검증

시작 파라미터는 서로 모순될 수 있어 서버에서 조합을 검증한다.

- 나이 ↔ 병역 상태 (19세 "필" 불가, 40세 "미필"은 사실상 면제 처리)
- 나이 ↔ 학력 ↔ 경력 (합계가 나이를 넘지 못함. 학업 기간 + 복무 기간 + 경력 ≤ 나이 − 취학 연령)
- 학력 ↔ 학자금 부채 (고졸에 학자금 대출 없음)
- 병역 특례복무 ↔ 자격증·학력 요건 (§8.1)

검증 실패 시 캐릭터 생성을 거부하고 어떤 조합이 모순인지 알려준다.

## 4. 시스템 아키텍처

```
client/  (webpack, 정적 SPA)
   │  REST (조작·조회) + SSE (시세·이벤트 푸시)
   ▼
server/  (Rust, axum)
   ├── api          HTTP 핸들러, 인증, 검증
   ├── clock        게임일 커서 전진, 배속 실행, 정산 큐
   ├── character    캐릭터 생성, 프리셋·포인트 예산 검증
   ├── market       거시·주식·금리·부동산·현물 시뮬레이션 엔진
   ├── product      계좌·금융상품 규칙 (CMA/ISA/IRP/연금저축/예적금…)
   ├── tax          세금·공제·4대보험 계산 (제도 버전 기반)
   ├── career       스펙·이력서·채용 매칭·급여
   ├── life         지출·생애 이벤트·파산/회생·복지 자격 판정
   ├── corp         법인 설립·단순 경영 손익
   └── store        MySQL (sqlx) 접근 계층
   ▼
MySQL  ── 세이브 상태 · 시세 시계열 · 제도 룰 데이터 · 감사 로그
```

### 기술 스택

| 계층 | 선택 | 비고 |
|------|------|------|
| 서버 | Rust 1.97.1, axum 0.8, tokio | 이미 스캐폴딩됨 (`server/`) |
| DB | **MySQL 8 + sqlx** | 확정 (§4.3). 시계열 볼륨이 커지면 `game_day` RANGE 파티셔닝 검토 |
| 클라이언트 | **TypeScript + webpack 5, 프레임워크 없음** | 확정. 구조는 아래 §4.1 |
| API 타입 공유 | Rust OpenAPI 생성 → TS 타입 코드젠 | `utoipa` 로 스키마를 코드에서 유도하고 `/swagger-ui` 로 노출. 코드젠은 후속 |
| 마이그레이션 | **sqlx migrate** | 확정 (§4.4). 서버가 기동하면서 `server/migrations/` 를 적용한다 |
| 인증 | **OAuth 2종(DataGSM · Google) + 세션 쿠키** | 확정 (§4.5). 비밀번호를 직접 보관하지 않는다 |
| 배포 | **홈서버 도커 + Vercel** | 서버는 홈서버 단일 컨테이너(nginx 뒤), 클라이언트는 Vercel. 구성은 `server/deploy/` |

### 4.1 클라이언트 구조 (프레임워크 없음)

프레임워크를 쓰지 않기로 했으므로, 프레임워크가 대신 해주던 일을 **얇은 자체 레이어로 명시적으로** 만든다.
아래 계층들이 화면을 늘리기 전에 먼저 세워야 하는 기반이다. 각 계층은 얇게 유지한다.

| 레이어 | 역할 | 설계 방향 |
|--------|------|-----------|
| reactive | 신호·파생값·부수효과 | 값을 읽은 문맥을 기억해 의존성을 자동 추적한다. 프레임워크의 세밀한 반응성을 대신하는 최소 코어 |
| hooks | 생명주기에 묶인 유틸 | `useSignal`·`useComputed`·`useEffect`·`useStoreValue`·`useDebounced`·`useThrottled`·`useAsync`·`useVisibility` 등. React 훅과 목적은 같지만 렌더가 없어 **호출 순서 규칙이 없다** |
| store | 서버 상태 보관·구독 | 경로 단위 구독(`subscribe('portfolio.cash', fn)`). 갱신 시 변경된 경로만 통지해 전체 리렌더를 피함 |
| view | 화면 단위 생명주기 | 각 화면은 `mount(el, ctx) → unmount` 규약. 구독 해제를 unmount에 모아 누수 방지 |
| router | History API 라우팅 | 경로 → 화면 매핑, 진입 시 데이터 프리페치 |
| form | 스키마 기반 폼 렌더러 | 캐릭터 생성·이력서·공고 검색이 전부 폼이라 **하나를 잘 만들어 재사용**하는 것이 핵심. 검증 규칙은 서버와 공유된 타입에서 유도 |
| api | REST 호출 + SSE 수신 | 생성된 타입을 쓰는 얇은 래퍼. SSE 이벤트는 store 액션으로만 반영 |

**타입 안전성으로 방어한다.** 프레임워크의 컴포넌트 계약이 없으니 타입이 유일한 안전망이다.
서버에서 OpenAPI 스펙을 생성하고 클라이언트 타입을 코드젠해, API 형태가 바뀌면 빌드가 깨지게 한다.
TypeScript는 `strict` + `noUncheckedIndexedAccess`까지 켠다.

**차트는 프레임워크 무관 라이브러리를 쓴다** (예: lightweight-charts, uPlot). 직접 그리지 않는다.

빌드는 webpack을 유지하되 TS 트랜스파일은 esbuild/swc 로더로 처리해 개발 반복 속도를 확보한다.
테스트는 store·form·계산 유틸에 집중한다 (DOM 통합 테스트는 최소).

> **이 결정의 위험**: 화면 수가 늘어날수록 손으로 만든 store/view 레이어의 유지비가 커진다.
> 위 레이어들을 얇게 유지하는 것이 곧 이 선택의 성공 조건이다. M3(커리어) 화면 규모에서
> 재평가하고, 그때 비용이 크면 store·api·form은 그대로 두고 view 레이어만 프레임워크로 교체한다
> (그래서 view를 나머지와 분리해 둔다).

### 4.2 게임일 전진 파이프라인

시간은 **플레이어의 요청으로만** 흐른다. 클라이언트가 canonical command ID와 최초 세이브 커서를 가진
`POST /advance` 또는 배속 실행을 요청하면 서버가 게임일을 한 칸씩 전진시킨다. 시장과 플레이어는 층이
다르다.

**층 1 — 시장 (플레이어와 무관, 버전·시드의 결정론적 경로)**

일봉은 `(모델 버전, 시드, 직전 시장 상태, 게임일별 혁신값)`으로 순서대로 생성한다. 마르코프 레짐과
GARCH처럼 직전 상태가 필요한 모델이므로 임의의 하루를 독립 난수로 뽑는다는 뜻은 아니다. 같은 버전과
시드의 day 0에서 출발하면 생성 배치 크기나 프로세스 재시작과 무관하게 전 구간이 같다는 뜻이다. 어떤
플레이어가 게임일 4,000까지 갔다면 뒤따라오는 플레이어는 **같은 값을 그대로 읽는다**. 생성 결과는
`market_daily`에 캐시하고 부족한 구간만 순서대로 채운다.

**층 2 — 플레이어 (스텝 1회당)**

1. **시장 조회** — 해당 게임일의 일봉을 읽음 (없으면 생성)
2. **평가** — 이 플레이어의 포지션만 재평가
3. **정산** — 이 게임일에 예약된 이자·배당·임대료·급여·지출·세금·대출 상환 처리
4. **이벤트** — 생애 이벤트 추첨, 채용 결과 판정, 복지 자격 재평가
5. **커서 전진** — 게임일 +1, 스냅샷 저장
6. **푸시** — SSE로 해당 세션에 델타 전송

정산은 `scheduled_settlement` 테이블에 **게임일 기준으로 예약**해 두고 커서가 그 날을 지날 때 처리한다.
1개월 스텝이나 x8 배속이면 이 루프를 서버가 연속 실행한다.

채용공고처럼 공유되는 결정론적 일별 카탈로그는 공개 중인 과거 구간을 읽기 전에 복원할 수 있어야 한다.
다만 순차 advance에서 현재 게임일의 공고 수가 pinned bundle의 일일 slot 합과 정확히 같다면 그 구간은
이미 완전하게 물질화된 것으로 보고 다음 하루만 생성한다. 현재 게임일이 0건이면 최초 실행·legacy 복원을
위해 전체 공개 구간을 다시 채우고, 0건도 완전한 개수도 아닌 부분 상태는 조용히 보정하지 않고 invariant
오류로 중단한다. 이 최적화는 생성 범위만 줄이며 공고 seed, `INSERT IGNORE` 멱등성, 하루별 player
transaction과 커서 전진 순서는 바꾸지 않는다.

수동 다일 명령은 명령 identity와 날짜별 append-only step을 함께 기록한다. 중간 실패 재시도는 마지막
완료 step 다음 날부터 재개하고, 전체 완료 때만 최종 receipt를 만든다. 캐릭터 시작도 같은 전역 command
identity를 사용해 응답 유실 재시도가 새 런을 중복 생성하지 않게 한다. 자동 배속 tick은 HTTP 응답 재시도
명령이 아니라 서버 런타임이 만든 단일 일일 실행이므로 step command 기록 대상이 아니다.

**서버가 시간의 권위를 갖는다.** 클라이언트는 "얼마나 진행할지"만 요청하고 경과 시간을 계산하지 않는다.
초당 최대 스텝 수를 제한해 배속 위조와 과부하를 함께 막는다.

**오프라인 자동 진행**(선택)은 별도 배치가 처리한다. 토글을 켠 플레이어만 대상으로, 마지막 접속 이후
상한(예: 게임 90일)까지 같은 루프를 돌린다. 토글이 꺼져 있으면 접속하지 않은 동안 세계는 멈춰 있다.

M0에서 먼저 구현하는 배속·일시정지 계약은
[`m0-game-loop.md`](./m0-game-loop.md)에 둔다. 배속도 서버가 실행하며, 클라이언트는 속도를 선택하거나
정지를 요청할 뿐 게임일을 추정하지 않는다. 오프라인 자동 진행은 이 계약과 분리해 M5에서 다룬다.

### 4.3 DB 선택 — MySQL

**MySQL 8 을 쓴다.** 팀·호스팅 환경에서 운영 경험이 흔하다는 것이 결정 이유다.
sqlx 가 동등하게 지원하므로 접근 계층 구현에는 차이가 없다.

대신 PostgreSQL 이면 공짜로 얻었을 두 가지를 **직접 만들어야 한다.** 잊으면 조용히 틀리는 지점이라 적어 둔다.

| 필요한 것 | PostgreSQL | MySQL 에서의 대응 |
|-----------|------------|-------------------|
| 제도 룰 JSON 조회 (§6, §8.2) | JSONB + GIN 인덱스 | JSON 컬럼 + **generated column 을 만들어 인덱싱** |
| 제도 버전 기간 겹침 방지 | `daterange` + EXCLUSION 제약 | **애플리케이션 로직으로 검증** — 같은 룰의 유효 기간이 겹치지 않는지 삽입 전 확인하고, `(domain, key, effective_from)` 유니크 인덱스로 보강 |
| 일봉 테이블 분할 | 선언적 파티셔닝 | `game_day` 기준 RANGE 파티셔닝 |
| 열거형 | 네이티브 enum | `VARCHAR` + 애플리케이션 검증 (Rust enum 이 이미 그 역할을 한다) |

기간 겹침 검증이 DB 제약이 아니라 코드에 있다는 점이 가장 큰 차이다. 세제 룰을 넣는 코드 경로는
**하나로 모아** 그 검증을 반드시 통과하게 한다 (여러 곳에서 직접 INSERT 하면 무너진다).

금액은 `BIGINT` 원 단위 정수로 저장한다 (DECIMAL·부동소수점 모두 쓰지 않는다).

서버와 MySQL 사이의 TCP 연결은 `TCP_NODELAY`를 켠다. 일일 정산은 한 transaction 안에서 권위 행을
순서대로 잠그고 검증하므로 독립 쿼리를 임의 병렬화할 수 없고, Nagle 지연이 쿼리 수만큼 누적되면 게임일
전진 자체가 막힌다. SQLx 0.9의 socket 회귀가 고쳐진 release가 나오기 전에는 crates.io의
`sqlx-core 0.9.0` 원본을 `server/vendor/sqlx-core/`에 checksum·license와 함께 고정하고, upstream 0.8.6에
있던 TCP·async-io `set_nodelay(true)`만 복원한 Cargo patch를 쓴다. DB·schema·정산 순서와 원자성은 바꾸지
않으며, 새 SQLx release로 교체할 때 vendor patch를 제거하고 실제 1일·30일 성능을 다시 확인한다.

### 4.4 스키마와 마이그레이션

**마이그레이션은 sqlx 가 한다.** SQL 파일은 `server/migrations/` 에 버전 순으로 두고, 서버가
기동할 때 `sqlx::migrate!` 로 적용한다. 별도 도구(JVM 기반 Flyway 등)를 두지 않는 이유는
sqlx 가 이미 의존성에 있고, 같은 파일을 테스트에서도 그대로 쓸 수 있기 때문이다.

첫 마이그레이션이 만드는 테이블은 넷이다.

| 테이블 | 역할 |
|--------|------|
| `user` | 계정. 어느 OAuth 로 들어왔는지(`provider`)와 그쪽 사용자 식별자를 함께 가진다 |
| `session` | 세션 쿠키 토큰의 **해시**와 만료. 토큰 원문은 저장하지 않는다 |
| `save` | 세이브 하나. 실행 세대·게임일 커서와 현금·부채. **계정 소유다** |
| `character` | 세이브에 딸린 캐릭터 (1:1) |

설계 원칙 세 가지를 지킨다.

- **금액은 모두 `BIGINT`**, 원 단위 정수다.
- **열거형은 `VARCHAR`** 로 저장하고 Rust enum 이 검증한다 (§4.3).
- **세이브는 계정에 속한다** (`save.user_id` 는 `NOT NULL`). 로그인 없이는 게임 상태가 없다.
- **새 캐릭터로 다시 시작할 때 실행 세대가 증가한다.** 같은 세이브의 게임일이 0으로 돌아가도 이전 실행의
  늦은 응답과 구분할 수 있어야 한다.

게임 상태의 권위는 DB 에 있다. 서버 메모리에 캐시를 두지 않는다 — 게임일 전진은 초당 수천 번
일어나는 연산이 아니고, 캐시를 두는 순간 재기동·다중 인스턴스에서 상태가 갈라진다.
SSE 브로드캐스트는 DB 쓰기가 커밋된 뒤에 흘린다.

### 4.5 인증 — OAuth 2종

**비밀번호를 직접 보관하지 않는다.** 로그인은 두 가지다.

| 제공자 | 대상 | 비고 |
|--------|------|------|
| **DataGSM** | GSM 구성원 | 학교 계정. `userinfo` 가 학년·반·학과까지 준다 |
| **Google** | 그 외 전부 | 표준 OIDC |

둘 다 **Authorization Code + PKCE(S256)** 를 쓰고, 서버가 `client_secret` 까지 함께 보낸다.
클라이언트는 secret 을 보지 않으며 토큰 교환은 전부 서버에서 일어난다.

제공자를 늘릴 수 있게 `OAuthProvider` 트레이트 하나로 추상화한다. 제공자마다 다른 것은
**엔드포인트 주소와 `userinfo` 응답 모양뿐**이고, 플로우(PKCE·state·토큰 교환)는 공통 코드가 처리한다.

#### 계정 식별

계정의 정체성은 **`(provider, provider_user_id)` 쌍**이다. 이메일이 아니다.

이메일을 키로 삼으면 두 가지가 깨진다. 같은 사람이 두 제공자로 들어왔을 때 한 계정으로 합쳐져
어느 쪽으로 로그인했는지 잃어버리고, 제공자가 이메일을 바꿔 주면 계정이 통째로 갈린다.
그래서 `email` 은 표시용으로만 저장하고 유니크 제약을 걸지 않는다.

#### 세션

로그인이 끝나면 서버가 임의 토큰을 만들어 **httpOnly · Secure · SameSite=Lax** 쿠키로 내린다.
DB 에는 그 토큰의 SHA-256 해시만 남긴다 — DB 가 새더라도 세션을 위조할 수 없다.

OAuth 왕복 동안 필요한 `state` 와 `code_verifier` 도 같은 성격의 짧은 쿠키(10분)에 담는다.
서버에 임시 상태를 두지 않으므로 재기동이 진행 중인 로그인을 끊지 않는다.

#### SSE 는 사용자별로 가른다

게임일 전진 틱은 세이브마다 다르다. 런타임이 인증 사용자별 브로드캐스트 채널을 소유하고 해당 사용자의
SSE만 그 채널을 구독한다. 전역 채널에서 `save_id`로 사후 필터링하지 않는다. 그래야 남의 전진이 내
화면에 흐르는 문제뿐 아니라, 다른 사용자의 빠른 틱 때문에 내 수신 버퍼가 밀려 연결이 끊기는 문제도 막는다.

## 5. 시장 시뮬레이션 엔진

목표는 "현실과 통계적으로 닮은" 시장이다. 실제 시세를 그대로 흘리는 것이 아니라,
**과거 데이터에서 추정한 파라미터로 생성**한다. 이 선택이 §10의 데이터 재배포 문제를 동시에 해결한다.

### 5.1 거시 레짐 (모든 자산의 공통 동인)

4상태 마르코프 체인: `확장 · 둔화 · 침체 · 회복`. 전이확률은 과거 경기순환 데이터로 추정.
레짐이 기준금리·물가·성장률의 드리프트를 결정하고, 그것이 아래 모든 자산군에 전파된다.

### 5.2 자산군별 모델

| 자산군 | 모델 | 주요 특성 |
|--------|------|-----------|
| 주식 (지수) | 레짐별 드리프트·변동성 + 변동성 클러스터링(GARCH 계열) | 침체기 하락 + 변동성 급등을 재현 |
| 주식 (개별) | 시장 팩터 + 섹터 팩터 + 개별 특이수익 | 베타·섹터 로테이션·분산 효과가 자연히 생김 |
| ETF | 기초지수 추종 + 보수·추적오차 | 국내/해외/채권/금 ETF |
| 금리·채권 | 단기금리 확률과정(Vasicek 계열) + 기간구조 → 채권가격 | 금리 인상기 채권 손실을 체감 |
| 예적금 | 기준금리 + 상품별 가산금리 스프레드 | 실제 금리 분포에서 추정한 스프레드 |
| 부동산 | 지역별 평균회귀 + 금리·공급 충격 + 전세가율 | 거래비용 크고 매도에 지연이 있음 |
| 현물 (금·은) | 실질금리 역상관 + 달러 연동 | 위기 시 헤지 성격 |
| 환율 | USD/KRW 확률과정 | 해외자산 수익률에 반영 |
| 물가 | 레짐 연동 CPI | 생활비·실질수익률에 반영 |

자산 간 상관은 개별로 지정하지 않고 **공통 팩터(레짐·금리·환율)를 통해 유도**한다.

### 5.3 캘리브레이션과 검증

- **캘리브레이션**: 과거 시계열로 연평균 수익률·변동성·레짐 전이확률·상관 추정 → 파라미터를 버전 있는 데이터로 저장
- **앵커링**: 외부 API로 받은 기준금리·물가·지수 수준을 새 월드의 시작점으로 사용. 진행 중인 월드는
  보정하지 않고 새 모델 버전·시드·앵커를 가진 새 월드만 추가한다.
- **검증 (자동 테스트)**: 장기 시뮬레이션을 다수 시드로 돌려 연평균수익률·변동성·최대낙폭·자산 간 상관이 역사적 범위 안에 들어오는지 통계 검정
- **재현성**: 시드 고정 시 완전 결정론적. 버그 재현과 리플레이에 필수

## 6. 금융 상품 (초기 구현의 핵심)

세제 혜택·한도·제약을 **실제 제도대로** 구현한다. 이 게임의 차별점이 여기에 있다.

아래 `✅`는 **초기 제품 범위에 포함한다는 뜻이지 현재 구현 완료 상태가 아니다.** 실제 구현 순서는 §12를 따른다.

| 상품 | 초기 구현 | 구현해야 할 실제 규칙 |
|------|:---:|------|
| 입출금·CMA | ✅ | 일복리 지급, RP형/발행어음형 금리 차이 |
| 예금·적금 | ✅ | 만기·중도해지이율, 이자소득세 15.4%, 예금자보호 한도 |
| ISA | ✅ | 연 납입한도·총 한도, 의무가입기간, 비과세 한도(일반형/서민형), 초과분 분리과세, 손익통산 |
| 연금저축계좌 | ✅ | 세액공제 한도, 연금수령 조건(만 55세·가입 5년), 연금소득세율, 중도해지 시 기타소득세 |
| IRP | ✅ | 세액공제 한도(연금저축 합산), 위험자산 70% 한도, 중도인출 제한 사유 |
| 국내주식·ETF | ✅ | 거래수수료·증권거래세, 배당소득세, 대주주 외 양도세 비과세 |
| 해외주식 | ✅ | 양도소득 기본공제 후 과세, 환율 반영, 배당 원천징수 |
| 채권 | ✅ | 표면이자 과세, 매매차익 처리, 듀레이션에 따른 가격 변동 |
| 금 현물 | ✅ | KRX 금시장 vs 골드바(부가세) 차이 |
| 부동산 | 🔸 M4 | 취득세·재산세·종부세·양도세(보유기간·주택수), 전세/월세, 담보대출 LTV·DSR |
| 대출 | 🔸 M4 | 신용/담보 구분, 금리 연동, DSR 규제, 연체 → 신용점수. **시작 부채(§3)도 이 엔진을 씀** |
| 금융소득종합과세 | ✅ | 연 2,000만원 초과 시 종합과세 — 세제 최적화의 핵심 제약 |

> **제도 데이터는 코드가 아니라 데이터로 둔다.** 세법·한도는 자주 바뀌므로 `policy_rule` 테이블에
> `effective_from` / `effective_to`를 갖는 버전 레코드로 저장하고, 엔진은 게임 시점에 유효한 룰을 조회한다.
> 실제 수치 확정은 구현 시점에 원문(국세청·금융위 고시)으로 검증한다. 이 문서의 서술은 설계 의도이며 법령 인용이 아니다.

## 7. 커리어와 개인 스펙

### 7.1 스펙 모델

| 항목 | 내용 |
|------|------|
| 학력 | 고졸 / 전문대 / 학사 / 석사 / 박사. 진학은 비용·시간 투자 (시작 시 선택 가능, §3) |
| 자격증 | 취득 조건(응시자격·학습시간·응시료), 직무별 가중치 |
| 어학 | 점수 구간, 유효기간 |
| 연수·교육 | 국비 지원 과정(고용24 연계)과 자비 과정 |
| 경력 | 직무별 연차. 경력이 연봉 밴드와 매칭 확률을 올림 |
| 프로젝트 | 포트폴리오 항목. IT·크리에이티브 직무 가중 |

시작 설정의 학력·경력·자격증은 이 스펙 테이블의 초기값으로 그대로 들어간다.
스펙은 **포트폴리오 / 이력서 / 링크드인 프로필** 세 가지 산출물로 조합되어 채용 매칭에 쓰인다.

### 7.2 구직 플랫폼

같은 공고 풀을 쓰지 않고 플랫폼마다 성격을 다르게 한다 — 어디를 쓰느냐가 선택이 되도록.

| 플랫폼 | 성격 | 게임 내 차별 요소 |
|--------|------|-------------------|
| 사랑방 | 지역 밀착, 중소·생산직 비중 | 지역 한정 공고, 빠른 채용. 출신 지역(§3)과 연동 |
| 잡코리아 | 전 업종 대량 | 공고 수 많고 경쟁률 높음 |
| 사람인 | 전 업종 대량 | 이력서 열람 기반 역제안 |
| 원티드 | IT·경력직 | 추천·리퍼럴 보너스, 합격 시 보상 |
| 링크드인 | 외국계·헤드헌팅 | 프로필 완성도가 인바운드 제안 확률을 결정 |
| 고용24 | 공공 연계 | 국비 훈련, 실업급여, 국민취업지원제도 등 제도 접근 창구 |

**매칭 로직**: 공고 요구 스펙과 플레이어 스펙의 적합도 점수 → 서류 통과 확률 → 면접 판정 → 연봉 밴드 내 오퍼.
초기 구현은 **업종 5~7개 중 선택해 취업하는 단순 버전**으로 두고, 공고·자격증 콘텐츠는 이후 채운다.

### 7.3 소득

급여는 4대보험·소득세 원천징수를 거쳐 세후로 입금되고, 연말정산에서 세액공제(연금저축·IRP 등)가 정산된다.
**여기서 §6의 세제 혜택과 연결되는 것이 이 게임의 핵심 루프다.**

## 8. 생애 시스템

아래 `✅`도 현재 완료 표시가 아니라 초기 제품 범위 표시이며, 구현 순서는 §12를 따른다.

| 시스템 | 초기 구현 | 내용 |
|--------|:---:|------|
| 지출 | ✅ | 고정비(주거·통신·보험)와 변동비, 물가 연동, 부양가족 수 반영 |
| 병역 | ✅ | 복무 형태 선택, 복무 기간 동안의 소득·경력 처리, 채용 자격 제약 (§8.1) |
| 복지·정책상품 | ✅ | 청년도약계좌·주택청약·실업급여·국민취업지원제도·근로장려금 등 자격 판정 엔진 |
| 법인 설립 | 🔸 단순 | 자본금·등록비, 업종별 기대손익, 급여 vs 배당 선택에 따른 세금 차이 체험. 세부 경영은 후속 |
| 개인파산·회생 | 🔸 M4 | 부채 초과 + 연체 지속 → 회생/파산 절차, 면책, 신용점수, 금융거래 제약 |
| 생애 이벤트 | 🔸 M4 | 질병·사고·결혼·부양가족 변화 등. 보험 가입 여부가 완충. 건강·배경(§3)이 확률에 반영 |

### 8.1 병역

한국 배경의 인생게임에서 병역은 **20대 초반 몇 년의 소득·경력·자산 축적을 통째로 결정**하는 변수다.
단순 공백이 아니라 선택지가 있는 시스템으로 다룬다.

| 복무 형태 | 요건 | 게임 내 효과 |
|-----------|------|--------------|
| 현역 | 기본 | 복무 기간 경력 공백, 병사 봉급 수준의 소액 소득, 자산 운용은 계속 가능 |
| 사회복무요원 | 신체등급 판정 | 출퇴근이라 복무 중 학업·자격증 취득 병행 가능 |
| 산업기능요원 | 자격증 + 지정업체 취업 | **복무 기간이 경력으로 인정** — 자격증 선투자가 커리어 가속으로 돌아오는 트랙 |
| 전문연구요원 | 석사 이상 | 학력 투자 트랙. 연구 경력 인정 |
| 장교·부사관 | 학력·선발 | 복무 기간이 길지만 급여가 병사보다 훨씬 높음 → 초기 자본 형성 경로 |
| 면제 | 신체·기타 사유 | 공백 없음. 캐릭터 생성 시 선택 가능하되 포인트 예산에서 대가 |
| 미필 유지 | — | 일부 공고가 "병역 필 또는 면제"를 요구해 **채용 풀이 좁아짐**. 나이가 차면 압박 증가 |

**자산 게임과 연결되는 지점**

- **장병내일준비적금** — 복무 중 납입에 정부 지원금이 매칭되는 정책상품. 소득이 거의 없는 시기에
  자산을 만드는 거의 유일한 수단이라, "복무 기간을 어떻게 쓰느냐"가 첫 최적화 문제가 된다
- 복무 기간에는 근로소득이 사실상 없으므로 **세액공제(연금저축·IRP)의 효용이 낮다** — 세제 혜택이
  소득 수준에 따라 달라진다는 것을 배우는 첫 사례
- 산업기능요원·장교 트랙은 스펙 선투자(자격증·학력)가 소득·경력으로 회수되는 구조라 §7과 직결

**예비군·민방위**는 연간 소액의 시간 비용으로만 반영한다 (세부 구현 불필요).

### 8.2 복지·정책상품 판정 엔진

복지상품은 **자격 조건 판정 엔진**으로 일반화한다 (나이·소득분위·재산·가구원·근로형태·병역 상태 조건의 조합).
개별 상품을 하드코딩하지 않고 조건식 데이터로 두면 콘텐츠 추가가 데이터 작업이 된다.
캐릭터 생성 시의 나이·지역·가구 구성·병역 상태가 곧바로 이 판정의 입력이 된다.

## 9. 데이터 파이프라인

### 9.1 과거 데이터 (캘리브레이션용, 배치 수집)

| 용도 | 후보 출처 |
|------|-----------|
| 금리·물가·통화·경기지표 | 한국은행 ECOS |
| 주가지수·개별종목 시계열 | KRX 정보데이터시스템 |
| 부동산 실거래·지수 | 국토부 실거래가, 한국부동산원 |
| 예적금·상품 금리 | 금융감독원 금융상품 공시 |
| 인구·소득·물가 통계 | KOSIS |

수집은 오프라인 배치로 돌려 원시 데이터를 저장하고, 여기서 파라미터를 추정해 **파라미터만 게임에 투입**한다.

### 9.2 외부 API (현재값 앵커링)

새 시장 월드의 시작점과 다음 캘리브레이션 버전 후보를 만드는 데만 쓴다. 이미 시작한 월드의 경로는
주기적으로 덮어쓰지 않는다. 어댑터 인터페이스로 감싸고 **장애 시 마지막 캘리브레이션 값으로 폴백**한다.
게임 진행이 외부 API 가용성에 의존하지 않는 것이 요구사항이다.

### 9.3 콘텐츠 데이터 (나중에 채움)

자격증 목록, 채용 공고 템플릿, 업종·직무 분류, 복지상품 조건, 지역 정보, 캐릭터 프리셋.
전부 시드 데이터 파일로 관리해 게임 로직 수정 없이 추가할 수 있게 한다.

## 10. 법적 · 윤리적 고려

비상업적 개인 프로젝트라 부담은 작지만, 실제 이름을 쓰는 만큼 짚어둘 것이 있다.

1. **시세 데이터 재배포** — 거래소·벤더 데이터는 재배포가 제한되는 경우가 많다. 이 설계는 외부 원시 시세를
   클라이언트로 그대로 내보내지 않고 **서버 내부 캘리브레이션에만 사용**하며, 플레이어가 보는 시세는
   시뮬레이션 산출물이다. 구현 시 각 API 이용약관을 개별 확인한다.
2. **상표** — 잡코리아·사람인·원티드·링크드인·사랑방·고용24 등은 타사 상표다. 서비스를 지칭하는
   명목적 사용에 한정하고, **로고·UI 모방은 하지 않으며, 제휴·후원 관계가 없다는 고지**를 넣는다.
   금융상품명도 마찬가지(제도 일반명 우선, 특정 회사 상품명은 회피).
3. **투자 조언 오인 방지** — "교육·오락 목적의 시뮬레이션이며 투자 조언이 아니고, 시세는 실제가 아닌
   생성 데이터"라는 고지를 상시 노출한다.
4. **차별 재현 회피** — §3.4. 성별·출신을 결과에 직접 곱하는 계수로 쓰지 않고, 제도를 통해 간접적으로만 반영한다.
5. **개인정보** — 계정 식별에는 OAuth 제공자와 제공자 사용자 ID를 쓰고, 이메일·표시 이름은 제공될 때만
   저장한다. 비밀번호·실명·주민번호·실제 금융정보는 수집하지 않는다.
6. **도박성 회피** — 실제 금전 투입·환전 경로를 만들지 않는다.

## 11. 미결정 사항

1. **배속 단위** — 자동 배속 x1~x8의 실제 초당 게임일 수, 그리고 오프라인 자동 진행 상한은
   플레이테스트로 조정.
2. **포인트 예산 설계** — 파라미터별 환산 비용을 어떻게 매길지. 밸런싱의 핵심이라 플레이테스트 의존도가 높다.
3. **캐릭터 수명 처리** — 사망·정년 이후를 엔딩으로 끊을지, 연금 수령기까지 계속 돌릴지. 목표 나이 도달 시
   결산 리포트를 주는 방식이 유력.
4. **시즌 운영 방식** — 시즌 공통 시드를 교체하는 주기와 프리셋별 리그의 시즌 길이.

## 12. 로드맵

현재 production 완료 상태는 **M0·M1·M2·M3·M4-A·M4-B·M4-C·M4-D1·M4-D2·M4-D3·M4-E1·M4-E2a와
M4-E2b 월 영업 정산까지**다. 로컬에는 E2b 운영 설정·대표 급여, E2c 법인세·배당·월 history와 M4-F의
스타일 없는 `/corporation` 조작 화면까지 구현되어 있으며 production migration `49·50` 인수 전에는 E2
완료로 표시하지 않는다. 기존 월드 v1·v2·v3와 그 월드에 고정된 런은
보존하고, M2-D 이후 새 런만 CPI·LLX·금 상품 묶음이 있는 v4를 사용한다. M3는 style 없는 기능 화면,
fresh MySQL 8 전진 마이그레이션과 실제 HTTP 스모크까지 완료했다. M3-C는 지급일 귀속 월 급여,
4대보험·원천징수·원장, 1월 1일 annual coordinator, 2월 정산, 연금 세액공제 allocation과 M2 금융소득
combined coordinator를 실제 employed·pension·combined 런으로 검증했다. M3-D는 복무 시작부터 전역까지
546일, 군 급여 18회, 장병내일준비적금 납입 18회·중도해지·만기·정부지원과 근로소득 연말정산을 실제
MySQL 8 및 public HTTP에서 검증했다. M4-A는 가구·거주지·CPI 생활비, 다음 달 예산 변경, 월말 필수액
연체와 일부·전액 상환, 20건 상환 window를 구현했다. 빈 DB와 실제 M3 DB의 전진 migration, 보존 런
compatibility, 4개월 public HTTP 진행, 명령 replay와 원장·부채 projection을 실제 MySQL 8에서 검증했다.
M4-B는 versioned 대출·신용 catalog와 runtime schema, 시작 부채 계약화, legacy bridge, 월별 상환·연체,
변동금리 reset, 일말 신용 평가, 세금 의무를 포함한 권위 부채 projection부터 상품·신용 조회, DSR quote,
신규 무담보 대출, 조기상환, 계약 상세와 dual-window 상환표·납부 이력까지 구현했다. 빈 DB와 기존 M4-A
세이브의 전진 migration, v1·v2 캐릭터 시작, 정상 납부·연체·명령 replay, 부분·전액 조기상환과 조회 cursor를
실제 MySQL 8과 public HTTP로 검증했다. M4-C1은 결정론적 지역 가격·임대료 지수, 월별 유한 매물,
동시 최초 조회 수렴과 `/housing` 조회 화면을 구현했다. 기존 disabled 모델과 새 active 모델 pin, 다른 속도의
두 런, 월 전환과 서버 재시작에서도 같은 응답을 실제 MySQL 8과 public HTTP로 검증했다. M4-C2a는 현금 전세
계약, 기존 보증금 반환, 새 보증금 지급, 이사비, residence 전환과 replay를 한 transaction으로 연결했다.
당월 생활비 pin 보존과 다음 달 새 지역·전세 기준 반영, 전세 간 재이사, 잔액 부족 rollback과 재시작 불변을
실제 MySQL 8과 public HTTP로 검증했다. M4-C2b1은 open-ended 월세 계약, 다음 달 1일 phase 300 청구,
전액·부분·0원 지급과 typed 연체, 수동 일부·전액 상환, 이사 시 미래 청구 취소를 구현했다. fresh migration,
명령 replay·충돌·실패 rollback, 원장·부채 projection과 서버 재시작 불변도 실제 MySQL 8과 public HTTP로
검증했다. M4-C2b2는 12개월 고정기간과 30일 전 정보성 갱신 안내, 같은 조건 자동 갱신, 월세 연체 60일
종료 검토 상태를 별도 term/action/review 이력으로 구현했다. 안내·갱신·검토의 정확한 경계일, 일부·전액
상환과 이사 해소, 과거 연체 보존, 명령 replay, 서버 재시작과 새 게임 cleanup을 실제 MySQL 8과 public
HTTP에서 검증했다. M4-C2c는 sealed credit v3에 전세보증금 80% 한도·고정 4%·24개월 만기일시상환
상품을 게시하고, 전용 quote의 신용·담보·소득·개발 상환여력 심사와 법정 DSR 비적용 근거를 저장한다.
eligible quote 실행은 대출금을 지갑에 입금하지 않고 전세보증금으로 직접 지급하며, 기존 clean linked
전세대출 상환·새 임대차·residence·원장·receipt를 한 transaction으로 묶는다. fresh MySQL 8에서 공개
취업 API로 검증 소득을 만든 뒤 소득 없음·담보 초과·적격 quote, 첫 이자 납부, 전세대출 대체상환,
현금 월세 이동의 자동상환, replay·충돌과 서버 재시작 복구를 public HTTP와 DB projection으로 검증했다.
M4-C3는 owner-occupied 단독 보유 capability, 현금 매수와 주담대 quote·직접 지급, 소유 residence·holding·
lien, 부대비용 원장과 순자산 projection을 구현했다. 현금 매수와 담보 매수, LTV 초과·적격 quote,
replay·충돌, 소유자의 임대차 이동 거절, 전액 조기상환과 담보권 해제를 fresh MySQL 8.4 및 공개 서버
MySQL 8.0의 격리 DB에서 HTTP와 DB projection으로 검증하고 모든 격리 자원을 삭제했다. M4-C4는 매도
주문·지연 체결, 주담대 일괄상환, 취득·보유·양도세와 원장·projection을 fresh MySQL 8.4 및 실제 HTTP에서
검증했다. M4-D1은 typed 복지 조건식, D-start evidence, 신청·승인·D+1 phase 150 지급과 원장을
SQLx `0038`, 스타일 없는 `/welfare`, 실제 MySQL 8.4·public HTTP로 검증했다. 기존 disabled pin 보존,
명령 replay·충돌, strict protocol, 서버 재시작 불변과 sealed catalog 보호도 확인했다. M4-D2는 sealed
event catalog, 독립 HMAC 월 후보, 선택·D+7 자동 만료·비용 원장과 `/events-insurance` 사건 기능을 SQLx
`0039`로 구현했다. 기존 unavailable run과 새 event v1 pin, 부양가족 0/1, support/decline/expiry,
small/big step·명령 replay·소유권/strict cursor와 재시작 hash를 실제 MySQL 8.4·public HTTP로 검증했다.
M4-D3 가상 보험의 계약·30일 보험료·비소급 claim·청구·만기와 스타일 없는 기능 화면은 커밋
`4b2b3db`에 구현했고 전체 로컬 검사를 통과했다. 격리 MySQL 8.4·public HTTP에서는 D0 가입 전 pin부터
D360 만기·12회 보험료, 서버 재시작 전후 DB/state hash 일치까지 확인했다. 당시 정리 전에 빠졌던
재시작 후 최종 aggregate·pin·orphan 검사는 사용자 지시에 따라 development production DB에서 별도 dump
없이 마쳤다. production MySQL 8.0.46의 migration `40/40`, 239 tables·11 views·719 triggers와 canonical
rehash를 확인했고, D0 pin 0 `notCovered` → D30 premium → D31 pin 1 ready/paid/replay를 재생했다. 서버
재시작 전후 HTTP와 contract/charge/pin/claim/cash/ledger를 포함한 18개 hash가 동일했으며 pin digest,
paid/reserved, allocation, cardinality, orphan, settlement, ledger balance와 wallet tie-out 위반은 전부 0이었다.
sealed update/delete도 SQLSTATE 45000으로 거절됐다. 운영 CD는 `aea745d`의 build heartbeat, `0b2c20b`의
직접 MySQL network, `eac0b92`의 populated `0023` backfill 수정을 거쳐 실행 `30314779686`에서 성공했고,
최종 수동 재시작 뒤에도 container healthy와 내부·외부 health HTTP 200을 확인했다. D3는 완료다.
M4-E1은 순수 `cashOnlyLiquidation` core, store/state와 여섯 strict API, client retry와 스타일 없는
`/recovery`를 구현했다. 별도 DB·dump 없이 development production CD를 수행해 migration `45/45`, 실패 0,
prepare/replay·composition 변경·withdraw·submit·배분·면책, strict API, 원장·채무·orphan 불변식과 container
재시작 전후 API hash 일치를 확인했다. 전세 quote·저장 quote 실행의 recovery overlay 도달성도 바로잡아
`creditRestricted/insolvencyRebuilding`을 확인했다. SQLx 0.9의 TCP Nagle 회귀는 검증된 upstream source를
vendoring하고 연결마다 `TCP_NODELAY`를 설정해 우회했다. production 30일 진행은 366.319867초에서
2.191241초로 줄었고 각 하루가 정확히 한 번씩 commit됐다. case 2는 day 1,855까지 `rebuilding`, exclusive
경계 day 1,856에서 transition 한 번으로 `recovered`가 되었으며 서버 재시작 전후 다섯 API hash가 같았다.
M4-E1의 전체 운영 인수 결과는 [M4 생애](./m4-life.md) §13.18에 기록했다. M4-E2a는 immutable 법인
catalog/policy와 설립 command, 개인 지갑·
개인 원장·분리 법인 원장을 한 transaction으로 연결했다. M4-E2b의 첫 slice는 HMAC-SHA256으로 결정되는 월
매출·변동비·고정비를 월 1일 pipeline에서 exact-once materialize하고 cash·미지급금·retained earnings와
법인 원장에 반영한다. production migration `48/48`, 첫 2026-08 월 row와 두 균형 원장, advance replay,
container 재시작 불변을 확인했다. 그 위 로컬 구현은 append-only 설정/receipt, M3 payroll·근로소득 재사용,
연 결산 법인세, 배당 원천징수와 M2 금융소득 연결, bounded month cursor와 server-authoritative client
화면까지 닫았다. 정확한 production 인수 순서와 다음 재개점은 [M4 생애](./m4-life.md) §1.1·§13.20을 따른다.
