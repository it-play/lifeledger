# M1 시장 코어 상세 스펙

- 작성: 2026-07-26
- 상태: M1-A·M1-B·M1-C 기능 구현 및 자동/실제 MySQL 검증 완료
- 상위 계획: [`development-plan.md` §2, §4.2, §5, §9, §12](./development-plan.md)

## 1. 단계와 현재 범위

M1은 기능 수직 슬라이스 세 단계로 나눈다.

1. **M1-A 시장 생성** — 월 단위 4국면, 단일 한국 주식 가격지수, 결정론적 일봉, DB 캐시,
   일일 파이프라인 연결, 현재 시장 스냅샷과 통계 검증
2. **M1-B 보유·매매·차트** — 현금으로 지수 상품을 사고파는 원자적 주문, 포지션 평가, 현재
   게임일까지로 제한한 히스토리 API, 프레임워크 독립 차트
3. **M1-C 금리 공통 팩터** — 정책금리 평균회귀, 채권 가격의 기반이 될 기간구조, 주식과 금리의
   공통 레짐 연결

세 단계는 모두 완료했다. v1·v2의 고정 경로를 보존하면서 신규 런 활성 포인터를 v3으로 옮겼고,
다음 구현 범위는 [`m2-accounts-tax.md`](./m2-accounts-tax.md)의 M2-A 원장·정산 기반이다. 실제 채권 보유,
ETF 분배금과 세금은 M2가 여기서 고정한 시장·금리 상태를 소비해 처리한다.

## 2. 월드와 버전

M1의 최초 월드는 다음처럼 고정한다.

- 월드 키: `m1-2026-v1`
- 시작일: `2026-01-01`
- 월드 시드: `20260101`
- day 0 지수 앵커: `100,000 KRW`
- 모드: M1에서는 모든 세이브가 이 공통 월드를 사용한다.

`2026-01-01`은 더 이상 임시 화면 상수가 아니라 이 월드의 불변 시작일이다. 외부 API의 현재값을
서버 기동 때마다 다시 읽어 과거 경로를 바꾸지 않는다. 새로운 앵커·시드·캘리브레이션은 기존 행을
수정하지 않고 새 월드와 새 버전으로 추가한다. 시즌 공통 시드와 자유 모드 개인 시드의 선택 UI는 M5에서
열지만, 세이브가 `market_world_id`를 가지게 해 저장 구조는 지금부터 분리한다.

M1-B 런타임은 캘리브레이션 버전별 생성기를 함께 유지하는 레지스트리를 사용한다.
`m1-2026-calibration-v1`은 주말 전용 달력 경로를 그대로 생성하고,
`m1-2026-calibration-v2`는 §8.4의 고정 KRX 달력 스냅샷을 사용한다. 등록되지 않은 버전은 추측해서
실행하지 않고 오류로 중단한다.

세 테이블을 사용한다.

- `market_calibration` — 버전 키와 검증된 생성 파라미터 JSON. 적용 뒤 불변이다.
- `market_world` — 월드 키, 시드, 시작일, 캘리브레이션 버전.
- `market_daily` — `(world_id, game_day)`별 생성 결과 캐시.

`market_daily`는 `game_day` 범위 파티션을 사용한다. MySQL 파티션 테이블에는 외래 키를 걸지 않고,
월드 존재 여부는 한 생성 경로에서 검증한다. 같은 월드·게임일은 유니크 키로 한 행만 허용한다.

## 3. 게임일과 시장일

- day 0은 거래 결과가 아니라 월드의 초기 앵커다.
- 세이브를 `d`에서 `d + 1`로 진행할 때 서버는 먼저 월드의 `d + 1` 시장일을 읽거나 생성한다.
- 그 시장일로 플레이어 평가·정산을 수행한 뒤 커서를 `d + 1`로 커밋한다.
- M1-A는 토요일·일요일만 휴장으로 본다. 휴장일도 `market_daily` 행은 만들되 직전 종가와 레짐을
  그대로 유지하고 일수익률은 0이다. 한국거래소 공휴일 달력은 M1-B에서 데이터로 추가한다.
- 레짐 전이는 거래일 21개마다 한 번 평가한다. 일봉마다 새 국면을 뽑지 않는다.

시장의 누락 구간은 플레이어 트랜잭션보다 먼저 별도 커밋해도 된다. 시장은 공유된 불변 순수 함수 결과라
미리 생성된 행이 플레이어 자산을 바꾸지 않기 때문이다. 그 뒤 플레이어 트랜잭션이 세이브 커서를 다시
잠그고 예상 `runRevision`·`gameDay`를 검증한 다음 `평가·정산 → 커서 증가`를 커밋한다. 커서가 달라졌으면
시장 캐시는 그대로 두고 최신 커서에서 제한 횟수만 재시도한다.

서로 다른 플레이어가 같은 누락 시장일을 동시에 만들면 둘 다 같은 값을 계산하며, 월드별 생성 잠금과
유니크 키·재조회로 하나의 캐시 행에 수렴한다. 이미 생성된 미래 일봉은 다른 플레이어에게 공개하지 않는다.

## 4. M1-A 생성 모델

### 4.1 거시 레짐

레짐은 `expansion · slowdown · recession · recovery` 네 상태다. OECD 한국 CLI의 장기평균 100 대비
수준과 방향으로 분류한 월별 국면을 전이 지속성의 근거로 쓴다. CLI에는 주가가 구성요소로 들어가므로
**전이확률·체류기간에만** 쓰고 주식의 국면별 기대수익을 같은 자료에서 다시 추정하지 않는다.

초기 전이행렬과 생성 파라미터는 `market_calibration.parameters`에 정수 basis point/ppm 단위로
저장한다. 월 자기전이확률은 역사 추정치에 맞춰 `0.84..=0.89`, 평균 체류기간은 `5..=10개월`을
검증 범위로 둔다.

### 4.2 단일 주식 가격지수

첫 지수의 계약은 다음과 같다.

- 심볼: `LLX`
- 표시명: `라이프 한국 종합지수`
- 성격: 배당을 포함하지 않는 한국 광범위 **가격지수**
- 종가: KRW 정수. 부동소수점으로 가격을 계산하지 않는다.
- 수익률: `parts per million (ppm)` 정수
- 조건부 분산: `ppm²` 정수

거래일 수익률은 레짐별 드리프트와 GARCH(1,1) 형태의 조건부 분산, 시드 기반 혁신값으로 만든다.
가격 갱신은 `i128` 중간값을 쓰는 고정소수점 연산 뒤 원 단위로 반올림하고, 모든 오버플로와 0 이하
가격을 오류로 처리한다. 난수는 `(world_seed, game_day, stream)`의 카운터 기반 순수 함수여야 하며
호출 순서나 프로세스 재시작에 의존하지 않는다. 알고리즘 변경도 캘리브레이션 새 버전이다.

M1-A는 가격지수만 만든다. M2에서 배당 정산을 추가할 때 이 가격수익률에 배당을 중복 포함하지 않는다.

## 5. 캘리브레이션 근거와 자동 검증

초기 근거는 OECD `Financial Market: Share Prices for Korea` 월별 가격지수와 OECD 한국 CLI다.
원시 시계열은 게임에 싣지 않고 오프라인 분석에만 사용한다.

- [OECD 한국 주가지수 계열을 제공하는 FRED 테이블](https://fred.stlouisfed.org/data/SPASTT01KRM661N)
- [KRX 지수정보포털](https://index.krx.co.kr/)
- [OECD CLI 해석 가이드](https://www.oecd.org/content/dam/oecd/en/data/methods/Interpreting_OECD_Composite_Leading_Indicators.pdf)
- [OECD Data Explorer](https://data-explorer.oecd.org/)

1990–2024 표본과 2000–2024 표본을 함께 감싸는 M1-A 회귀 범위는 다음과 같다. 이는 기관이 공표한
보장값이 아니라 고정 표본에서 계산한 **구현 검증 범위**다.

| 지표 | 여러 고정 시드의 25~35년 경로 집계 범위 |
|------|------------------------------------------|
| 가격 CAGR | 2% ~ 5% |
| 연환산 변동성 | 17% ~ 22% |
| 최대 낙폭 | -75% ~ -45% |
| 월 절대수익률 1차 자기상관 | 0.15 ~ 0.35 |
| 월 자기전이확률 | 0.84 ~ 0.89 |
| 평균 레짐 체류 | 5 ~ 10개월 |

통계 테스트는 단일 시드가 모든 범위에 들어오는지를 요구하지 않는다. 고정된 여러 시드의 중앙값과
분포를 검사해 우연한 한 경로 때문에 테스트가 흔들리지 않게 한다. 동일 시드의 완전 결정론, 다른 시드의
분기, 휴장일 가격 유지, 정수 가격 안전성은 별도 단위 테스트로 고정한다.

## 6. 저장·파이프라인 계약

`market_daily`에는 최소한 다음을 저장한다.

- `world_id`, `game_day`, `market_date`, `market_open`
- `session_index`, `regime`
- `equity_close_krw`, `equity_return_ppm`, `equity_variance_ppm2`, `equity_residual_ppm`

`equity_residual_ppm`은 마지막 거래일의 충격 상태다. 휴장일에는 수익률만 0으로 두고 이 잔차를
직전 값으로 유지해, 주말을 지날 때마다 다음 거래일의 GARCH 변동성 군집이 인위적으로 사라지지 않게 한다.

시장 생성기는 순수 도메인 모듈이고 MySQL을 모른다. 저장소만 캘리브레이션·직전 일봉을 읽고 생성기를
호출한다. 현재 일봉 조회와 누락 구간 생성은 하나의 저장소 경로로 모아 임의 `INSERT`를 막는다.

M1부터 `DailyPipeline` 서비스가 `MarketStore`와 `SaveStore`를 조합한다. 시장 저장소가 목표 일봉을 먼저
보장하고, 세이브 저장소는 예상 커서를 조건으로 플레이어 하루를 원자적으로 커밋한다. `load`는 현재
커서의 일봉이 없는 오래된 개발 세이브를 위해 day 0부터 현재 day까지 결정론적으로 보충할 수 있다.
플레이어 DB 커밋 뒤에만 시장이 포함된 게임 스냅샷을 SSE로 보낸다.

## 7. API와 기능 중심 화면

`GameSnapshot`에 다음 읽기 전용 시장 상태를 추가한다.

```json
{
  "market": {
    "world": "m1-2026-v1",
    "date": "2026-01-02",
    "open": true,
    "regime": "expansion",
    "index": {
      "symbol": "LLX",
      "name": "라이프 한국 종합지수",
      "closeKrw": 100123,
      "dailyReturnPpm": 1230
    }
  }
}
```

M1-A 대시보드는 종가·일수익률·레짐·개장 여부를 텍스트로만 표시한다. 이번 단계에서는 스타일이나 차트를
추가하지 않는다.

M1-B의 히스토리 API는 인증된 세이브의 `gameDay`를 상한으로 강제한다. 전역 캐시에 더 먼 미래 일봉이
있어도 뒤처진 플레이어에게 반환하면 결정론적 미래를 누설하기 때문이다. 범위와 응답 개수에도 상한을 둔다.

## 8. M1-B 보유·매매·히스토리 계약

### 8.1 상태 순서와 커서

`save.state_revision BIGINT UNSIGNED`를 추가한다. 한 런 안에서 플레이어 상태를 커밋할 때마다 증가하며,
하루 전진도 현금·포지션 평가·정산이 들어갈 같은 트랜잭션 경계이므로 1 증가한다. 체결 주문도 게임일을
바꾸지 않고 1 증가한다. 배속 선택·일시정지처럼 DB에 저장하지 않는 런타임 제어는 증가시키지 않는다.

새 캐릭터로 런을 시작하면 `run_revision`을 1 증가시키고 `state_revision`은 0으로 초기화한다. 보유 포지션은
모두 비우고 시작 현금·부채로 되돌린다. 서버의 낙관적 커서는
`(market_world_id, run_revision, state_revision, game_day)` 네 값을 쓰며, 일일 전진과 주문 모두 실제
`UPDATE` 조건에서 네 값을 다시 검사한다.

모든 `GameSnapshot`은 `stateRevision`을 포함한다. HTTP와 SSE를 합치는 클라이언트의 적용 순서는
`runRevision → stateRevision`이다. `gameDay`는 표시와 시장 조회에 쓰지만 상태 순서의 대체 키가 아니다.
SSE 이벤트 ID도 `runRevision:stateRevision`으로 바꾼다. 같은 revision의 재전송은 같은 상태로 보고 허용하되,
앞선 revision을 늦게 받은 응답은 버린다.

### 8.2 LLX 포지션과 주문

첫 상품은 `LLX` 한 종목이다. 수량은 양의 정수이고 공매도·신용매수·부분 체결은 없다. 한 주문과 한 런의
총 보유수량은 각각 `1..=1,000,000`주로 제한한다. 체결가는 요청을 처리할 때 세이브의 현재 게임일에
확정된 LLX 종가다. `market_open = false`인 날에는 주문을 거절한다.

플레이어 데이터는 다음 두 테이블로 나눈다.

- `asset_position` — `(save_id, symbol)`별 현재 수량과 총 취득원가
- `trade_execution` — 클라이언트 주문 ID, 런·상태 revision, 게임일, 매수/매도, 수량, 체결가,
  총 체결금액과 매도 시 제거한 취득원가를 남기는 append-only 체결 원장

`POST /api/portfolio/orders` 요청은 다음 계약을 쓴다.

```json
{
  "orderId": "4f521f4c-9dd8-4d20-8e1f-15cb13cbe0f2",
  "expectedRunRevision": 3,
  "expectedStateRevision": 42,
  "expectedGameDay": 17,
  "side": "buy",
  "symbol": "LLX",
  "quantity": 10
}
```

`expected*` 값은 사용자가 화면에서 본 스냅샷에 주문을 묶는다. 첫 전송 자체가 늦어져 새 캐릭터나 다음
게임일에 도착하면 재호가해 체결하지 않고 `busy`로 거절하며, 클라이언트가 새 스냅샷에서 다시 제출해야 한다.

`orderId`는 클라이언트가 한 제출 시도에 한 번 생성하는 canonical UUID 문자열이다. `(save_id, order_id)`를
유니크하게 두고, 네트워크 재시도로 같은 주문이 다시 오면 원장에 저장된 expected revision·side·symbol·quantity를
비교한다. 모두 같으면 재체결하지 않고 현재 스냅샷을 반환한다. 하나라도 다르면 idempotency 충돌로
거절한다. 동일 주문 replay는 원래 DB 커밋 뒤 응답 조립이 실패한 경우의 복구 경계이기도 하므로, 현재
스냅샷을 SSE에도 다시 보낸다. 같은 revision 재전송은 §8.1의 멱등 적용 규칙으로 안전하다.

매수는 `price × quantity`를 checked 정수 연산으로 계산하고 현금이 충분할 때만 현금 차감·수량 증가·
취득원가 증가·원장 기록·`state_revision + 1`을 한 MySQL 트랜잭션으로 커밋한다. 매도는 보유수량이 충분할
때만 반대로 처리한다. 일부 매도의 제거 취득원가는
`floor(total_cost_basis × sold_quantity / quantity_before_sale)`이고 전량 매도는 남은 취득원가 전부를
제거한다. M1-B의 수수료·거래세·배당은 모두 0이며 M2 도입 뒤 과거 체결에 소급하지 않는다.

응답은 `execution`과 갱신된 `snapshot`을 함께 가진다. execution에는 주문 ID·종목·방향·수량·체결가·
총액·0원 수수료·0원 세금과 `replayed` 여부가 들어간다. 스냅샷의 `portfolio.positions`는 종목·수량·총 취득원가·평균단가·
현재가·평가금액을 포함하고, `portfolio.marketValueKrw`는 모든 포지션 평가금액 합계다.
`netWorthKrw = cashKrw - debtKrw + portfolio.marketValueKrw`로 계산한다. 모든 금액 곱셈·합산은 checked
정수 연산이며 표현 범위를 넘으면 체결이나 스냅샷 생성을 실패시켜 부정확한 값을 내보내지 않는다.

주문 실패 코드는 `invalidOrder · characterRequired · marketClosed · insufficientCash ·
insufficientQuantity · positionLimit · idempotencyConflict · busy`로 고정하고 사용자 메시지는 한국어로 둔다.
체결 뒤 서버는 같은 스냅샷을 해당 사용자의 SSE 채널에도 보낸다.

### 8.3 인증된 시장 히스토리

`GET /api/markets/LLX/history?days=N`을 추가한다. `days` 기본값은 365, 허용 범위는 `1..=3660`이다.
서버는 인증된 사용자의 세이브를 먼저 읽고 응답 상한을 그 세이브의 현재 `game_day`로 강제한다. 요청자가
미래 game day를 직접 지정하는 파라미터는 제공하지 않는다.

응답은 `world`, `symbol`, `throughGameDay`와 오름차순 `points`를 가진다. 각 포인트는 `gameDay`, `date`,
`open`, `closeKrw`, `dailyReturnPpm`, `regime`을 포함한다. 전역 캐시에 더 먼 미래가 있어도 절대 반환하지
않는다. `DailyPipeline.load`가 현재 day까지 캐시를 보장하므로 조회는 그 범위 안에서만 수행한다. 저장소
SQL도 `save.market_world_id`와 `market_daily.game_day <= save.game_day`를 조인 조건으로 다시 적용해,
다른 프로세스에서 런이 바뀌어도 서비스 계층의 상한만 믿지 않는다.

### 8.4 KRX 휴장일과 월드 버전

현재 `m1-2026-v1`의 주말 전용 달력은 그대로 보존한다. 휴장일을 같은 버전에 추가하면 거래 세션 번호와
시드 경로가 바뀌므로 금지한다. M1-B는 별도 월드 `m1-2026-v2`와 달력
`krx-equity-2026-rules-v1`을 추가한다.

달력은 런타임 외부 API를 호출하지 않고 저장소에 체크인한 2026~2060 CSV 스냅샷을 사용한다. 각 행은
`date, provenance, label`을 가지며 provenance는 다음 중 하나다.

- `krxPublished` — KRX 연간 휴장일 공표에서 확인
- `statutoryProjected` — 고정한 관공서 공휴일 규정과 월력 자료로 계산
- `krxRuleProjected` — 근로자의 날·연말 휴장 규칙으로 계산
- `manualKrxOverride` — 이후 확인된 임시·선거·거래소 재량 휴장

2027년 이후 값은 공식 KRX 확정일이 아니라 규칙 기반 전망임을 데이터 메타데이터와 문서에 명시한다.
새 공식 공표가 전망과 다르면 기존 CSV나 월드를 수정하지 않고 새 달력·캘리브레이션·월드 버전을 만든다.
생성기 레지스트리는 캘리브레이션 버전별 생성기를 함께 보관해 v1 세이브를 계속 읽을 수 있어야 한다.

활성 월드 선택은 불변 `market_world` 행을 수정하지 않고 별도 단일 할당 레코드가 가리킨다. 기존 런은
배정된 v1을 유지하고, 새 세이브와 새 캐릭터 런부터 활성 v2를 배정한다. 이후 시즌 교체도 같은 경계를
재사용한다. 할당 레코드는 삭제·재삽입하지 않고 제자리 변경마다 증가하는 revision을 가진다. 새 런은 `(worldId, assignmentRevision)`을
읽어 day 0을 먼저 보장한 뒤, 세이브 트랜잭션에서 같은 할당을 잠그고 다시 확인한다. 할당이 중간에
A→B→A로 돌아와도 revision 차이로 감지해 준비부터 제한 횟수 안에서 재시도하며, 시장 준비 실패나 할당
충돌은 `runRevision`을 증가시키지 않는다.

### 8.5 기능 중심 클라이언트

대시보드에 포지션 수량·평균단가·평가금액과 매수/매도 주문 폼을 추가한다. DOM은 mount에서 한 번 만들고
스냅샷 신호가 바뀔 때 텍스트와 disabled 속성만 갱신한다. 주문 폼은 기존 `lib/form`과 zod 경계를 사용하며
스타일은 추가하지 않는다.

히스토리는 기간 선택과 텍스트 표를 먼저 제공한다. 차트는 프레임워크 독립 라이브러리 `uplot@1.6.32`를
고정해 종가 한 개 시리즈만 표시한다. 라이브러리 필수 CSS 외의 시각 스타일은 만들지 않는다. 차트는
`create*()` 팩토리와 `DisposableBag`으로 `destroy`·resize 정리를 소유하며, 캔버스를 읽지 못하는 사용자를
위해 같은 데이터의 텍스트 표를 유지한다.

### 8.6 M1-B 완료 조건

1. 같은 주문 ID 재전송은 한 번만 체결되고 다른 payload 재사용은 거절된다.
2. 동시 주문·일일 전진이 현금·수량을 잃어버리지 않고 상태 커서 충돌 시 제한 횟수 안에서 재시도한다.
3. 잔액 부족·보유수량 부족·휴장일·오버플로는 어떤 행도 부분 커밋하지 않는다.
4. 새 런은 포지션을 비우고 활성 v2 월드를 받으며 기존 v1 런 경로는 바뀌지 않는다.
5. 히스토리는 인증된 세이브의 현재 게임일 뒤를 반환하지 않고 3660행 상한을 지킨다.
6. HTTP·SSE의 늦은 응답은 `runRevision → stateRevision` 순서로 걸러진다.
7. 대시보드에서 LLX를 사고팔고 평가액과 텍스트 히스토리·기능형 차트를 확인할 수 있다.
8. 서버 테스트·clippy·fmt, 클라이언트 테스트·타입 검사·린트·프로덕션 빌드와 실제 MySQL 8 스모크가 통과한다.

### 8.7 M1-B 구현 결과

2026-07-26 기준으로 LLX 원자적 매수·매도, 포지션 평가, append-only 체결 원장, 인증된 현재
게임일까지의 히스토리, 상태 revision 기반 HTTP·SSE 병합과 기능형 uPlot 차트를 연결했다. 같은 주문의

## 11. M1-C 금리 공통 팩터 계약

### 11.1 버전과 범위

M1-C는 `m1-2026-calibration-v3`과 `m1-2026-v3`을 추가한다. v1·v2의 캘리브레이션, 월드,
캐시 행은 수정하지 않는다. 활성 월드 포인터는 v3으로 옮기되 기존 런은 자신에게 저장된 월드를 계속 쓴다.
v3은 v2의 `krx-equity-2026-rules-v1` 달력을 그대로 사용하고 다음 금리 팩터를 추가한다.

- 한국은행 기준금리에 대응하는 `policyRateBp`
- 국고채 기간구조를 단순화한 `treasury3mBp · treasury1yBp · treasury3yBp · treasury10yBp`
- 정책금리 변화가 같은 날 주식 수익률에 주는 `equityRateShockPpm`

M1-C는 금리와 수익률곡선을 생성·저장·표시하는 단계다. 실제 채권 보유·쿠폰·만기상환·매매는 M2에서
이 곡선을 소비한다. CPI와 명목소득 물가연동도 M2 정산 엔진에 함께 넣는다.

v3의 day 0은 2026-01-01 당시 유효했던 한국은행 기준금리 2.50%를 `250bp`로 고정한다. 이후 발표된
실제 금리로 진행 중인 월드를 덮어쓰지 않는다. 새 실측 앵커가 필요하면 새 월드 버전을 만든다.
[한국은행 기준금리 변경 이력](https://www.bok.or.kr/portal/singl/baseRate/list.do?menuNo=200656)과
[2% 물가안정목표](https://www.bok.or.kr/portal/main/contents.do?menuNo=200291)는 앵커와 장기 중립 수준의
근거이며, 생성 결과를 실제 전망으로 해석하지 않는다.

### 11.2 정수 평균회귀 과정

모든 금리는 basis point 정수다. 정책금리는 거래 세션 21개마다, 그 경계에 해당하는 개장일에만 한 번
갱신한다. 휴장일과 경계가 아닌 개장일에는 직전 값을 유지한다. 월별 갱신은 다음 순서로 수행한다.

1. 현재 레짐의 장기 목표금리와 직전 정책금리의 차이에 평균회귀 계수를 곱한다.
2. `(worldSeed, gameDay, ratePolicyStream)`으로 만든 독립 혁신값을 더한다.
3. 가장 가까운 25bp로 반올림하고 `0..=800bp`로 제한한다.
4. 새 정책금리와 직전 정책금리의 차이를 `policyRateChangeBp`로 기록한다.

초기 캘리브레이션은 다음 정수값을 사용한다. 조정은 기존 버전을 수정하지 않고 v4 이상에서 한다.

| 항목 | 초기값 |
|------|-------:|
| 중립 정책금리 | 250bp |
| 월 평균회귀 계수 | 250,000ppm |
| 월 혁신 표준 크기 | 25bp |
| 하한 / 상한 | 0bp / 800bp |
| 확장 목표 | 350bp |
| 둔화 목표 | 250bp |
| 침체 목표 | 100bp |
| 회복 목표 | 200bp |

혁신값의 정규 근사는 주식 생성기와 같은 고정 정수 분위수 표를 쓰되 stream 번호는 분리한다. 호출 순서,
프로세스 재시작, 다른 월드의 생성 여부가 결과를 바꾸면 안 된다. 계산 중간값은 `i128`이고 범위 초과나
잘못된 캘리브레이션은 포화값으로 숨기지 않고 오류로 처리한다.

### 11.3 기간구조와 주식 연결

수익률곡선은 정책금리와 중립금리의 가중 평균에 만기별 기간 프리미엄을 더한 고정소수점 함수다.
정책금리 갱신일과 레짐 전환일에 다시 계산하고 그 밖의 날에는 유지한다.

| 만기 | 현재 정책금리 가중치 | 중립금리 가중치 | 기간 프리미엄 |
|------|---------------------:|----------------:|---------------:|
| 3개월 | 900,000ppm | 100,000ppm | 5bp |
| 1년 | 750,000ppm | 250,000ppm | 15bp |
| 3년 | 500,000ppm | 500,000ppm | 30bp |
| 10년 | 250,000ppm | 750,000ppm | 60bp |

각 만기 금리는 `0..=1,500bp` 범위이고 원 단위 채권 가격 계산에 쓰기 전까지 백분율 부동소수점으로
바꾸지 않는다. 금리 인상기 채권 손실은 M2가 이 저장된 만기수익률의 전일 대비 변화를 사용해 계산한다.

같은 월별 경계에서 정책금리가 바뀌면 v3 주식 수익률에
`equityRateShockPpm = -policyRateChangeBp × 300ppm`을 더한다. 25bp 인상은 그 날 주식 수익률에
`-7,500ppm`, 인하는 `+7,500ppm` 충격을 준다. 레짐은 주식 드리프트와 정책금리 목표를 함께 결정하고,
정책금리 변화도 주식에 직접 들어가므로 상관계수를 결과에 맞춰 따로 지정하지 않는다. 최종 수익률은
기존 가격 양수·오버플로 검증을 그대로 통과해야 한다.

### 11.4 저장·API·화면

`market_daily`에 v3 전용 금리 열을 nullable로 추가한다. v1·v2 행의 `NULL`은 “금리 0%”가 아니라
“이 월드 버전에는 금리 팩터가 없음”이다. v3 생성기는 다섯 만기/정책금리와 변화·주식 금리충격을 모두
채우며, 일부만 채워진 행은 손상된 캐시로 보고 읽기를 실패시킨다.

시장 스냅샷과 히스토리 포인트는 `rates`를 nullable 객체로 제공한다. 활성 v3 런에서는 항상 객체이고,
v1·v2 기존 런에서는 `null`이다. 객체는 `policyRateBp`와 네 만기 국고채 금리만 공개한다.
`policyRateChangeBp`와 `equityRateShockPpm`은 재현·검증용 저장 상태이며 공개 API에는 내보내지 않는다.

클라이언트는 시장 화면에 기준금리와 네 만기를 텍스트 표로 표시한다. 백분율 표시는 bp를 소수 둘째 자리
퍼센트로 포맷할 뿐 계산에 다시 사용하지 않는다. 금리 전용 차트와 스타일은 추가하지 않는다.

### 11.5 M1-C 완료 조건

1. 같은 v3 월드와 게임일은 생성 순서·재시작과 무관하게 동일한 금리곡선과 주식 종가를 만든다.
2. v1·v2의 고정 회귀 벡터와 기존 캐시가 바뀌지 않고 등록되지 않은 calibration은 명시적으로 실패한다.
3. 정책금리는 21번째 거래 세션에만 25bp 단위로 바뀌고 항상 `0..=800bp`에 머문다.
4. 고정 다중 시드 장기 경로에서 확장기의 평균 정책금리가 침체기보다 높고 모든 만기금리가 허용 범위다.
5. 같은 조건에서 금리 인상 충격은 주식 수익률을 낮추고 인하 충격은 높이는 순수 규칙 테스트가 통과한다.
6. 활성 v3의 현재·히스토리 API와 스타일 없는 시장 표에서 정책금리와 기간구조를 확인할 수 있다.
7. 서버 자동 검증과 실제 MySQL 8 마이그레이션·캐시 생성 스모크가 통과한다.

### 11.6 M1-C 구현 결과

2026-07-26 기준으로 v3 정책금리·수익률곡선 생성, 주식 금리충격, nullable 레거시 캐시, 현재·히스토리
API와 스타일 없는 금리 표를 연결했다. v1·v2 고정 회귀 벡터는 그대로 유지했고 v3 새 런만 활성
포인터를 따른다. 정책금리 갱신 세션·25bp 양자화·범위·레짐별 장기 평균·충격 방향을 순수 규칙으로
검증했으며, 일부만 채워진 DB 금리 행은 손상으로 거절한다.

통합 기준 서버 138개 테스트와 clippy·fmt, 클라이언트 101개 테스트와 타입 검사·린트·프로덕션 빌드가
통과했다. 공개 서버의 MySQL 8.0.46에 만든 PII 없는 격리 DB에서 `0001`~`0008` 전체 마이그레이션,
v3 완전 금리 행과 v1 nullable 레거시 행 저장, 부분 금리 행과 잘못된 주식 충격의 CHECK 거절을 확인했다.
검증 뒤 임시 DB와 파일을 삭제했고 운영 DB의 스키마와 데이터는 변경하지 않았다.
